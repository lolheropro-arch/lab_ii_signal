# Mini Shazam: ข้อมูลสำหรับทำสไลด์

เอกสารนี้สำหรับ agent ที่จะทำสไลด์นำเสนอ ใช้ตัวเลขตามนี้ และคงคำเตือนเรื่องความน่าเชื่อถือไว้

## กติกาสำหรับคนทำสไลด์

- ภาษาในสไลด์: ไทย ศัพท์เทคนิคเป็นอังกฤษได้
- โฟกัส: **การค้นหาเพลงจากเสียงเพลงที่เปิดจริง**
- **ห้ามพูดถึงโหมดฮัมเพลง** ยังอยู่ระหว่างพัฒนา แม้จะเห็นไฟล์ `hum.py` และ `melodies.py` ในโฟลเดอร์
- ระบุให้ชัดว่าตัวเลขไหน **วัดจากบอร์ดจริง** และตัวเลขไหน **จำลอง**
- ผลจากบอร์ดส่วนใหญ่เป็นการวัดรอบเดียวหรือไม่กี่รอบ ห้ามเขียนเป็น "ความแม่นยำ X%" ของระบบจริง
- ห้ามเขียนว่า "ไมค์ 4 ตัวลด noise ได้ดี" ผลที่วัดไม่ได้สนับสนุนข้อนี้ ดูหัวข้อการทดลอง

## 1. โปรเจกต์นี้คืออะไร

**Mini Shazam** คือระบบจำเพลงจากเสียงที่เปิดให้ไมค์ฟัง ได้แรงบันดาลใจจากแอป Shazam เลยอยากลองทำเอง โดยรับเสียงผ่านฮาร์ดแวร์ของ Lab และแสดงผลบน Python GUI

ผู้ใช้เปิดเพลงใกล้ไมค์แล้วกดปุ่ม ระบบจะตอบชื่อเพลงและตำแหน่งในเพลง พร้อมกราฟเปรียบเทียบ และเล่นเสียงที่อัดหรือท่อนเพลงที่คล้ายกันให้ฟังเทียบได้

โจทย์ Mini Project กำหนดให้ใช้ข้อมูลที่สตรีมจากฮาร์ดแวร์ และต้องทำมากกว่าการแสดงกราฟ FFT หรือ spectrogram ทั่วไป

## 2. สิ่งที่ใช้

| ส่วน | รายละเอียด |
|---|---|
| ไมค์ | โมดูลไมค์ analog ปรับ gain ได้ ไฟเลี้ยง 3.3 V ไบแอสเอาต์พุตประมาณ 1.65 V |
| ADC | MCP3201 ความละเอียด 12 บิต อ่านด้วย SPI ที่ 800 kHz |
| FPGA | Terasic DE10-Lite (MAX 10, `10M50DAF484C7G`) ภาษา VHDL บน Quartus Prime 20.1 |
| MCU | ESP32-S3 UNO ใช้ Arduino core และ FreeRTOS |
| ส่งเข้าคอม | USB-serial ผ่าน CH340 ที่ 921600 baud |
| ซอฟต์แวร์ | Python: NumPy, SciPy, librosa, pyserial, Matplotlib, Tkinter, SQLite |

## 3. เส้นทางข้อมูล

```
ไมค์ ─► ตัวต้านทาน ─► MCP3201 ─► FPGA ─► SPI ─► ESP32-S3 ─► USB ─► Python GUI
                     12 บิต   ping-pong  1 MHz    คิว 6 บล็อก  921600  fingerprint + SQLite
```

| ค่า | ปัจจุบัน |
|---|---|
| ตั้งค่า Sample rate | 42 kS/s (`FS_HZ` ใน `fpga/task3_audio.qsf`) |
| Sample rate จริงตามการหาร | ประมาณ 42,017 S/s เพราะ 50 MHz หาร 42,000 ไม่ลงตัว |
| ขนาดบล็อก | 1024 sample (ประมาณ 24.4 ms ต่อบล็อก) |
| SPI FPGA→ESP32 | Mode 0, 1 MHz, 2060 ไบต์ต่อบล็อก (ใช้ประมาณ 16.5 ms) |
| USB ESP32→คอม | 2070 ไบต์ต่อบล็อก ใช้ราว 85 kB/s จากเพดานประมาณ 92 kB/s |
| Python | ลดเหลือ 8 kHz ก่อน fingerprint และ 16 kHz ตอนเล่นเสียง |

Task 3 ใช้ 16 kS/s แต่ Mini Project แยกโค้ดออกมาและเลือก sample rate ตามผลทดลองได้เอง

หมายเหตุ: คอมเมนต์หัวไฟล์ FPGA และ sketch ยังเขียน 16 kS/s, SPI 4 MHz หรือ MCP3202 ตามของเดิม ให้ยึดตารางนี้ และ ESP32 บนบอร์ดยังไม่ได้ upload sketch รุ่นที่ตั้งค่า header เป็น 42000 ซึ่ง Mini Shazam ไม่ได้อ่านค่านี้จึงยังทำงานได้

## 4. Hardware timer, DMA และ ping-pong buffer

| เทคนิค | ใช้ไหม | อยู่ตรงไหน |
|---|---|---|
| **จังหวะสุ่มจากฮาร์ดแวร์** | **ใช้** | `sample_tick_gen.vhd` นับคล็อก 50 MHz เป็นวงจรใน FPGA ไม่ได้พึ่งซอฟต์แวร์ |
| **Ping-pong buffer** | **ใช้** | `audio_block_buffer.vhd` BRAM 2 ธนาคาร ธนาคารละ 1024 ค่า |
| **Hardware timer ของ MCU** | **ไม่ใช้** | ESP32 ไม่ได้เป็นตัวสุ่มเสียง Fs จึงไม่ขึ้นกับจังหวะซอฟต์แวร์ของ ESP32 |
| **DMA ที่เขียนสั่งเองในโค้ด** | **ไม่มี** | sketch ใช้ `SPI.transferBytes()` ตรงๆ และไม่ได้ตั้งค่า DMA เอง |
| **Interrupt และ RTOS** | **ใช้** | ขา DRDY ปลุกงาน SPI ผ่าน ISR และ semaphore แยกงาน SPI ไว้ core 0 กับงาน USB ไว้ core 1 |
| **บัฟเฟอร์ฝั่ง ESP32** | **ใช้** | pool 6 บล็อก พร้อมคิว `freeQ` และ `fullQ` |

Ping-pong ทำงานแบบนี้: ADC เขียนธนาคารหนึ่งจนเต็ม แล้วสลับไปอีกธนาคาร ส่วน SPI อ่านธนาคารที่เขียนจบแล้ว ฝั่งเขียนไม่ต้องหยุดรอฝั่งอ่าน จังหวะสุ่มจึงไม่ถูก SPI รบกวน

## 5. ยืนยันว่าข้อมูลครบและไม่เสีย

| ชั้น | สิ่งที่ตรวจ | ถ้าเจอปัญหา |
|---|---|---|
| **FPGA** | ส่ง status `0xC3`, sync `0xA55A`, `SEQ`, `FLAGS`, จำนวน `N`, checksum และนับ `DROPS` | ถ้าบล็อกค้าง จะนับ drop และ `SEQ` ยังเดินต่อ |
| **ESP32 (รับจาก SPI)** | ตรวจ status, sync, `N`, บิต valid และ checksum | ไม่ส่งบล็อกนั้นต่อ และนับ `spi_errs` |
| **ESP32 (ส่งออก USB)** | ใส่ sync `AA 55 33 CC`, seq, ตัวนับ error/drop, เวลา และ checksum | ถ้าคิวเต็ม จะนับ `esp_drops` |
| **Python** | หา sync ใหม่เอง ตรวจความยาวและ checksum | ทิ้ง frame เสีย |
| **Python (ลำดับ)** | ตรวจเลข `seq` | ถ้าบล็อกหาย เติมด้วยค่า DC เพื่อไม่ให้เวลาเลื่อน |

**Checksum** คือผลรวม sample ทั้งบล็อก mod 2^16 จับ bit error ทั่วไปได้ แต่ไม่ใช่ CRC จึงจับกรณีสลับลำดับ sample ไม่ได้

**ผลตรวจลิงก์:** บอร์ดจริงไม่มีบล็อกหายใน `--check 10` ที่ 16 kS/s ส่วนที่ 42 kS/s พบบล็อกหาย 5 จาก 1,522 (ประมาณ 0.33%) และมีรอบหนึ่ง 4 จาก 300 จึงควรพูดว่าเหลือระยะเผื่อ USB น้อย

## 6. หลักการจำเพลง

ขั้นตอนเป็นแนวเดียวกับ audio fingerprinting ของ Shazam:

1. **เตรียมเสียง:** ลบ DC, ลดเหลือ 8 kHz, normalize
2. **Spectrogram:** STFT หน้าต่าง Hann, NFFT 1024 (7.8 Hz ต่อช่อง), HOP 256 (32 ms ต่อเฟรม)
3. **Constellation map:** หาจุดยอดเฉพาะพื้นที่ในช่วง 300–3800 Hz และต้องดังกว่า median อย่างน้อย 10 dB
4. **Hash:** จับคู่จุดยึดกับจุดถัดไปไม่เกิน 10 จุด เก็บ `(f1, f2, dt)` ระยะเวลาห่างไม่เกิน 63 เฟรม (ประมาณ 2 วินาที)
5. **ค้นในฐานข้อมูล:** หา hash ที่ตรงกันใน SQLite
6. **Offset histogram:** คำนวณ `offset = t_เพลง − t_คลิป` ถ้าเป็นเพลงเดียวกัน hash จำนวนมากจะกองที่ offset เดียว

### การให้คะแนน

| ค่า | ความหมาย | เกณฑ์ |
|---|---|---|
| `score` | จำนวน hash ที่ offset ตรงกัน (ยอมคลาด ±1 เฟรม) | ≥ 12 |
| `ratio` | `score ÷ คู่แข่ง` | ≥ 2.5 |

คู่แข่งคือเพลงอันดับ 2 หรือยอดอื่นในเพลงเดียวกัน โดยตัด 4 ยอดสูงสุดออกก่อน เพราะอาจเป็นท่อนซ้ำ

ต้องผ่านทั้งสองข้อ จึงจะตอบชื่อเพลง คะแนนไม่ใช่เปอร์เซ็นต์ และไม่มีเพดาน 100 คลิปที่ยาวกว่ามักได้คะแนนสูงกว่า

**ระบบไม่ได้เทียบ waveform ตรงๆ** กราฟ waveform และ spectrogram ของ candidate มีไว้ให้คนดูเท่านั้น

### ฟีเจอร์ใน GUI ที่ควรโชว์

- กราฟ waveform, spectrogram + จุดยอด, offset histogram
- กราฟท่อนเพลง candidate ใช้แกนเวลาเดียวกับคลิป และซ้อนจุดยอดของเพลงกับเสียงที่อัด
- เลือก candidate ได้ และเล่นเสียงที่อัดสลับกับท่อนที่คล้ายได้

## 7. ผลการค้นหาเพลง

### วัดจากบอร์ดจริง (เปิดเพลงจากมือถือ)

ฐานข้อมูลมี 4 เพลง: Für Elise, Eine Kleine Nachtmusik, สามัคคีชุมนุม, เพลงอวยพรวันเกิด เพลงที่ทดสอบในตารางนี้คือ Für Elise

| เงื่อนไข | ความยาวคลิป | score | ratio | ผล |
|---|---|---|---|---|
| 32 kS/s | 15 วินาที | 1311 | 11.1 | ถูก |
| 32 kS/s | 8 วินาที | 269 | 6.4 | ถูก |
| 42 kS/s | 15 วินาที | 1065 | 8.1 | ถูก |
| 42 kS/s | 8 วินาที | 651 | 10.2 | ถูก |
| 42 kS/s, ไมค์ 4 ตัว | 10 วินาที | 254 | 4.9 | ถูก |
| 42 kS/s, ไมค์ 1 ตัว | 10 วินาที | 233 | 5.5 | ถูก |

ตัวเลขในตารางนี้มาจากคนละท่อนเพลงและคนละระดับเสียง จึง **ห้ามนำมาเทียบว่า sample rate ไหนจำเก่งกว่า**

**ตัวเปรียบเทียบเชิงลบ (วัดจริง):** เสียงห้องเปล่าได้ score 4–5 และ ratio 1.0–1.25 ระบบตอบว่าไม่พบ ส่วนเพลงจากลำโพงคอมซึ่งเข้าไมค์เบา อันดับ 1 เป็นเพลงถูก (score 24–109) แต่ ratio แค่ 1.7–1.9 จึงตอบว่าไม่พบ

### จำลอง (คลิป 8 วินาทีตัดจากไฟล์ ไม่ผ่านไมค์)

White noise ชุดละ 100 คลิป:

| SNR | ตอบถูก | ตอบผิดอย่างมั่นใจ |
|---|---|---|
| ไม่ใส่ noise | 100 | 0 |
| 5 dB | 100 | 0 |
| 0 dB | 98 | 0 |
| −5 dB | 92 | 0 |

เพลงที่ไม่มีในฐานข้อมูล (leave-one-out, SNR ไม่ใส่/5/0 dB รวม 300 คลิป): ตอบผิด 0 คลิป

เสียงแอร์จริงที่อัดไว้ผสมกับคลิปเพลง ชุดละ 16 คลิป:

| SNR | ตอบถูก |
|---|---|
| 5 dB | 16 |
| 0 dB | 16 |
| −6 dB | 16 |

## 8. การทดลองและข้อสรุป

### 8.1 ไมค์ 1 ตัวเทียบ 4 ตัว

**ไอเดีย:** ต่อไมค์ 4 ตัวผ่านตัวต้านทาน 5.1 kΩ เท่ากันเข้าจุดเดียว แรงดันที่จุดรวมคือค่าเฉลี่ยตามทฤษฎีบท Millman โค้ดจึงไม่ต้องเปลี่ยน เพราะ ADC ยังเห็นแรงดันเส้นเดียว

**ที่คาดไว้:** เสียงรบกวนที่ไม่สัมพันธ์กันควรลดได้สูงสุดประมาณ 6 dB ส่วนเสียงความถี่ต่ำจะหักล้างยาก เพราะความยาวคลื่นที่ 300–1000 Hz คือ 34–114 ซม. ใหญ่กว่าระยะแถวไมค์ราว 15 ซม.

**ผลจากบอร์ด (10 วินาที เปิดเพลงจากมือถือ):**

| ค่า | 4 ไมค์ | 1 ไมค์ |
|---|---|---|
| score / ratio | 254 / 4.9 | 233 / 5.5 |
| rms รวม | 16.4 | 58.3 |
| แถบ 300–1000 Hz | 6.8 | 48.9 |
| แถบ 1000–2000 Hz | 10.7 | 21.9 |
| แถบ 2000–3800 Hz | 2.2 | 7.3 |
| แถบ 4000–8000 Hz | 4.0 | 4.7 |
| แถบ 8000–16000 Hz | 4.1 | 4.3 |

อีกรอบที่ต่อเนื่องกัน ช่วงละประมาณ 5 วินาที: 4 ไมค์ score 167, ratio 3.0 และ 1 ไมค์ score 248, ratio 19.1

**ข้อสรุปที่เขียนได้:**
- จำเพลงได้ทั้งสองแบบ และรอบ 10 วินาทีคะแนนใกล้กัน
- รอบนี้ 4 ไมค์ **ไม่ได้ลดเสียงซ่าอย่างชัดเจน** และสัญญาณเพลงในรอบนี้เบากว่าไมค์เดี่ยวมาก

**ห้ามสรุปเกินข้อมูล:** ยังไม่รู้สาเหตุที่ 4 ไมค์เสียงเบากว่า อาจเกิดจากเสียงถึงไมค์ไม่พร้อมกัน, gain ไม่เท่ากัน หรือไมค์เดี่ยวอยู่ใกล้ลำโพงกว่า และยังไม่ได้ปรับ gain ทีละตัว ท่อนเพลงของแต่ละรอบก็ต่างกัน

### 8.2 เพิ่ม Sampling rate

**ปัญหา:** วงจรไม่มีตัวกรอง anti-aliasing แบบ analog สัญญาณที่สูงกว่า Nyquist จะพับลงมา

**หลักฐานการพับความถี่ (วัดจริง):**

| ความถี่จริงที่เห็นตอน 32 kS/s | ตอน 16 kS/s พับไปที่ | วัดได้ตอน 16 kS/s |
|---|---|---|
| ประมาณ 13.7 kHz | ประมาณ 2.3 kHz | 2334 Hz |
| ประมาณ 9.1 kHz | ประมาณ 6.9 kHz | 6832 Hz |

**ตอนเงียบ ก่อนทดลองปิดแอร์ (หลังลดเหลือ 16 kHz เพื่อเทียบกัน แต่ละค่ามาจากคนละช่วงเวลาและเสียงห้องเปลี่ยนได้):**

| แถบ | 16 kS/s | 32 kS/s | 40 kS/s |
|---|---|---|---|
| 2000–3800 Hz | 7.4–8.4 | 2.3–5.1 | 3.4–3.8 |
| 4000–6000 Hz | 7.4 | 6.4–7.3 | 4.9 |
| 6000–7800 Hz | 7.2–7.3 | 1.5–1.7 | 4.3 |

**ข้อสรุปที่เขียนได้:**
- จาก 16 เป็น 32 kS/s ลดเสียงรบกวนในช่วงจำเพลงได้ชัด เพราะสัญญาณความถี่สูงพับลงมาทับน้อยลง
- จาก 32 เป็น 40 kS/s เสียงรบกวนแค่ย้ายแถบ รวมแล้วไม่ดีขึ้นชัดเจน
- 42 kS/s ถูกเลือกจากการฟังแบบไม่รู้เฉลย 1 รอบเทียบ 32 kS/s ผู้ฟังให้ 42 kS/s ดีกว่า แต่สองไฟล์มีระดับเสียงต่างกัน (rms 21.2 กับ 16.0) ส่วนการวัดตอนปิดแอร์ สองค่านี้แทบเท่ากัน
- การเพิ่ม sample rate ช่วยเรื่อง aliasing ไม่ได้กำจัดเสียงรบกวนทั้งหมด และแลกกับระยะเผื่อ USB ที่น้อยลง

**เทียบระหว่างการทดลอง:** สำหรับเสียงรบกวนช่วงจำเพลง การเพิ่มจาก 16 เป็น 32 kS/s ให้ผลชัดกว่าการเปลี่ยนจาก 1 เป็น 4 ไมค์ ส่วนการเพิ่มความดังของเพลง รอบนี้ไมค์เดี่ยวดังกว่า ยังไม่ควรสรุปว่า sample rate หรือจำนวนไมค์ทำให้การจำเพลงแม่นขึ้น เพราะ score ยังเทียบกันข้ามรอบไม่ได้

| แถบแถว 13.6–13.9 kHz | 5.2 | 0.22 |
| ต่อแถบ 2 kHz ช่วง 2–16 kHz | 2–6.5 | 0.5–1.0 |

**ผลการฟังล่าสุดของผู้ทดลอง:** ไม่มีเสียงรบกวนรุนแรงแล้ว เหลือเล็กน้อยในระดับยอมรับได้ ควรนำเสนอว่าเป็นการประเมินด้วยการฟัง ไม่ใช่ค่าที่วัดได้

ปิดแอร์แล้วเสียงรบกวนช่วงสูงลดลงมากที่สุดในการทดลองทั้งหมด ยังไม่รู้ว่าเข้ามาทางเสียงหรือทางไฟฟ้า และไม่ได้เปิดกับปิดสลับหลายรอบ

เมื่อปิดแอร์ เสียงพูดห่างไมค์ 5 ซม. มีช่วงดังเทียบช่วงเบา 28.7 dB เทียบกับ 14 dB ในรอบก่อนปิดแอร์ แต่เป็นการพูดคนละครั้ง จึงเป็นแค่แนวโน้ม

### 8.4 ตัวกรองเสียงในโปรแกรม

- **ตัวกรองเสียงแอร์:** band-pass 120–4000 Hz + notch ความถี่ที่ดังค้าง ใช้เฉพาะตอนเล่นเสียง เสียงสูงกว่า 4 kHz ลดจาก 11.7–11.9 เหลือ 1.5 แต่แถบ 300–1000 Hz ไม่ลด
- **ไม่ใช้กับการจำเพลง:** ทดสอบแล้วคะแนนลดลงราว 40% และที่ SNR −6 dB ตอบถูกลดจาก 16 เป็น 14 ชุดละ 16 คลิป
- **ตัวเลือกลดเสียงแบบ spectral gating:** ผู้ใช้ฟังแล้วไม่ดีกว่า จึงปิดเป็นค่าเริ่มต้น

## 9. ปัญหาที่เจอและวิธีแก้

| ปัญหา | อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|---|
| ข้อมูลเลื่อน 1 บิต | PC ไม่ได้รับ frame เลย | อ่าน `0xC3` เป็น `0x86` ESP32 ปฏิเสธทุกบล็อกแบบเงียบ | เลื่อนบิตกลับในฝั่ง ESP32 ต้นเหตุในฮาร์ดแวร์ยังไม่ยืนยันด้วย scope |
| ไม่รู้ว่าลิงก์ติดตรงไหน | ไม่มีข้อความใดๆ | Sketch ทิ้งข้อมูลเงียบๆ | เพิ่มบรรทัด `#ESP32 alive` รายงานสถานะ |
| รูปแบบ frame ไม่ตรง | โปรแกรมต่อกับบอร์ดไม่ได้ | Python คาด frame คนละแบบกับ Task 3 | เขียนตัวรับใหม่ พร้อม checksum และ `seq` |
| Error พอร์ต | ขึ้น Input/output error | โปรแกรมเลือก `/dev/ttyS31` | เรียงพอร์ต USB ขึ้นก่อน |

| FPGA ไม่ส่งข้อมูล | MISO อ่านได้ `0xFF` | `.sof` หายเมื่อถอดไฟ | โปรแกรมใหม่หลังเสียบไฟ |

| ต่อ GND ผิด | ไฟลัดตอนต่อไมค์ 4 ตัว | สาย GND เสียบผิดตำแหน่ง | แก้สายแล้ววัดไฟ 3.3 V ปกติ ยังไม่พิสูจน์ว่าไมค์ทุกตัวไม่เสียหาย |
| เสียงจี่ | เสียงพูดฟังยาก | เสียงจากแอร์/ห้อง และการพับความถี่ | เพิ่ม sample rate, ปิดแอร์ และกรองตอนเล่นเสียง |

## 10. ข้อจำกัดและงานต่อ

- ฐานข้อมูลมีแค่ 4 เพลง ยังไม่รู้พฤติกรรมเมื่อฐานข้อมูลใหญ่
- ยังไม่ได้ทดสอบหลายเพลงและหลายรอบผ่านไมค์จริงเพื่อหาอัตราความแม่นยำ
- วงจรยังไม่มีตัวกรอง analog ก่อน ADC (แนวทางที่ยังไม่ทดสอบ: 10 nF ที่ขา IN+ ลง GND ตัดราว 7 kHz ตามการคำนวณ)
- USB เหลือระยะเผื่อน้อยที่ 42 kS/s
- การเลื่อน 1 บิตยังเป็นการแก้ที่อาการ ควรตรวจด้วย scope
- ไมค์ 4 ตัวยังไม่ได้ปรับ gain ทีละตัว

## 11. โครงสไลด์ที่แนะนำ

1. Mini Shazam คืออะไร และแรงบันดาลใจจาก Shazam
2. ภาพรวมระบบ: ไมค์ → ADC → FPGA → ESP32 → Python
3. การรับข้อมูล: Fs จาก FPGA, ping-pong, SPI, USB
4. ความถูกต้องของข้อมูล: checksum, sync, seq และการนับ drop
5. หลักการจำเพลง: spectrogram → จุดยอด → hash
6. การเทียบและให้คะแนน: offset histogram, `score`, `ratio`
7. หน้าจอโปรแกรมและการเปรียบเทียบ candidate
8. ผลการค้นหาเพลง
9. การทดลองไมค์ 1 ตัวเทียบ 4 ตัว
10. การทดลอง sampling rate และหลักฐาน aliasing
11. ผลของแอร์และตัวกรองเสียง
12. ปัญหาที่เจอและวิธีแก้
13. ข้อจำกัดและงานต่อ
